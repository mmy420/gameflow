# GameFlow

**批次驱动、三执行体、状态机落盘的 Windows 游戏资源归档流水线。**

把「资源页 → 网盘转存 → 下载 → 解压 → 校验 → 删源包 → MTool 加载翻译」这条重复的人工链条，
拆成可重跑、可中断、每一步都有显式状态的作业。

> **状态**：设计阶段。详尽设计规格见 [`SPEC.md`](SPEC.md)，**尚未落地**。
> **目标平台**：Windows（本仓库在 macOS 上撰写，只存文档与规则，不存游戏数据）。

---

## 它解决什么

现状是一套每次都要手动重复七遍的流程：从资源站拿到页面 → 页面给出多个网盘链接 → 逐个网盘转存 →
本地建游戏名文件夹 → 下载 → 解压 → 如需要用 MTool 加载翻译。而且实际工作对象**从来不是一个游戏，是一组**。

麻烦集中在解压这一段：压缩包**通常有密码**、**有多重嵌套**、**有时要改文件名后缀才能正确解开**。

GameFlow 把这条链条拆成三个执行体，各自的可无人值守程度不同：

| 执行体 | 触发 | 无人值守 | 用 Computer Use | 干什么 |
|---|---|---|---|---|
| **A · 巡检** | Windows 任务计划 | 是 | 否 | 扫描、下载完成判定、只读预检、认领归位、写状态、出对账报告 |
| **B · 作业** | 人 / Codex 交互触发 | 否 | 否 | 解压、递归解包、逐条目校验、Defender 预检、删源包 |
| **C · 前台** | 人显式触发，短会话 | 否 | 是 | 资源页解析、网盘转存下载、MTool 加载翻译、最终验收 |

A + B 合起来是用户要求的「不使用 Computer Use 的阶段一」，C 是「使用 Computer Use 的阶段二」。

**为什么阶段一还要再切一刀**：需要密码和需要提权的步骤**不能**放进无人值守的计划任务——
S4U 登录类型不存储密码（解不开 DPAPI 密码库），`MpCmdRun` 要求提权运行。这是被官方文档逼出来的切分，不是偏好。

## 设计原则

**确定性优先。不猜。**

- 密码不猜 —— 只走 P0→P6 的确定性优先级链，加上 ≤4 个有明确语义的等价展开（原样 / 去空白 / UTF-8↔GBK 互转）。字典爆破、从游戏名推导、从 README 里「读懂」一段话，全部硬性禁止。
- 类型不猜 —— 7-Zip 本来就按内容嗅探，不传具体 `-t` 类型名（传了反而会把能自动处理的情况变成硬失败）。
- 规则不猜 —— 改后缀、重建分卷序列这类动作必须由批次条目显式声明。
- 不自适应、不学习、不加权评分。所有分支要么由显式规则决定，要么**停下来落一个具名状态等人**。

**删除是本项目风险最高的操作。** 源包与游戏本体同目录、解压后自动删除，意味着不可撤销、无回收站兜底——
判错一次就是永久数据丢失。所以删除被 12 条与条件 gate 住，且由已落盘的状态决定，不现场重判。

默认策略是**尺寸门控的两段式删除**：小于 2 GiB 的源包先进 3 天 trash，大包直接删。
理由是误判概率与磁盘代价的分布不重合——最容易被误判的恰恰是小包（纯文本汉化补丁），而磁盘压力只在大包上成立。
这条是 SPEC 里唯一标记为**待你签收**的策略选择（§12.2），要字面遵守「解压完成后自动删除」就把 `trash_days` 设成 0。

**引擎层吝啬，呈现层不吝啬。** 对账报告要真正好读。

## 目录

```
gameflow/
  README.md      ← 你在这里
  SPEC.md        ← 详尽设计规格（§1-§12）
  docs/
```

落地后在 Windows 上的布局是两个根：`D:\GameFlow`（脚本与规则，进 Git）和 `D:\GameLib`（数据，不进 Git）。
库根压到 10 个字符是 MAX_PATH 预算需要——建目录的实际上限是 248 而不是 260，而日文游戏名加多重嵌套很容易撞破。

## 从哪开始

**M0 是跑 `Preflight.ps1` 并把 §11 里最高优先级的几条实测掉。**

这不是仪式感。本 SPEC 在 macOS 上撰写，凡是 Windows 特有的行为都只能靠官方文档推断，
文档里标了 `【待测】` 的地方不实测就写不出正确的实现。其中四条会实质改变设计：

1. 环境快照 —— 装的到底是 7-Zip CLI 还是只有 WinRAR/Bandizip GUI、系统 ANSI 代码页、文件系统类型
2. Codex 沙盒能否写到 `D:\GameLib`（不能的话执行体 A 根本跑不起来）
3. `prefix_rule` 对 PowerShell 的拆分语义（不通过的话每次解压都要人点一次，A 就失去无人值守的意义）
4. 浏览器扩展驱动已登录浏览器时是否占用前台 —— **这条决定阶段一/阶段二的分界线画在哪**

之后按 A（只读）→ B（先关掉删除）→ B（打开删除）→ C 的顺序推进。

## 出处

本 SPEC 的需求来自 Codex 会话「规划 Windows 游戏资源工作流」
（`01a08eba-1b68-7b33-9a7e-242a5be1c22a`，2026-09-10）。该会话确立了批次驱动与两阶段拆分的方向。

在此基础上做了六条技术线的事实核查与一轮对抗式事实仲裁，推翻了原方案中的若干断言——
其中影响最大的三条是：Codex 内置浏览器**没有**按任务指定下载目录的能力、
「改后缀」在绝大多数情况下**根本不需要**、以及游戏目录名的真实约束不是「非 ASCII」而是
「必须能在系统 ANSI 代码页内无损表示」。详见 §1.6 的对照表与 §12 决策台账。
