# GameFlow

**批次驱动、三执行体、枢纽模型的 Windows 游戏资源归档流水线。**

把「资源页 → 网盘转存 → 下载 → 解压 → 校验 → 删源包 → 投递到目标盘」这条重复的人工链条，
拆成可重跑、可中断、每一步都有显式状态的作业。

> **状态**：设计阶段。详尽设计规格见 [`SPEC.md`](SPEC.md)，**尚未落地**。
> **目标平台**：Windows（本仓库在 macOS 上撰写，只存文档与规则，不存游戏数据）。

---

## 它解决什么

现状是每次都要手动重复一遍的流程：从资源站拿到页面 → 页面给出多个网盘链接 → 逐个转存 →
本地建游戏名文件夹 → 下载 → 解压 → 如需要用 MTool 加载翻译。而且实际工作对象**从来不是一个游戏，是一组**。

麻烦集中在解压这一段：压缩包**通常有密码**、**有多重嵌套**、**有时要改文件名后缀才能正确解开**。

## 一次批次长什么样

```
你（约 3 分钟）        建批次：给一组链接 + 提取码 + 解压密码 + 目标路径
你（约 2 分钟）        在网盘客户端里转存 + 排进下载队列（下载目录只设一次）
                      ↓
A · 巡检（自动）       每 10 分钟一轮：判下载完成 → 认领归位 → 只读预检 → 写状态
B · 作业（自动）       密码链 → 解压 → 递归解包 → 逐条目校验 → Defender → 删源包
B · 投递（自动）       把只剩游戏本体的目录整体移到 <目标盘>\<分组>\<游戏名>\
                      ↓
你（30 秒）           全批跑完后看一次对账报告
```

**中途不需要你介入**，也不占用前台桌面。第一阶段（下载→解压→投递）**完全用不到 Computer Use**。

## 三个执行体

| 执行体 | 触发 | 无人值守 | 用 Computer Use | 干什么 |
|---|---|---|---|---|
| **A · 巡检** | 计划任务（Interactive / Limited） | 是 | 否 | 下载完成判定、认领归位、只读预检、写状态、出报告 |
| **B · 作业** | 计划任务（Interactive / **Highest**）或手动 | 是 | 否 | 解压、校验、Defender、删源包、投递 |
| **C · 前台** | 人显式触发，短会话 | 否 | 是 | **只剩 MTool 翻译**；网盘下载与资源页解析都是可选 |

**为什么阶段一要切成 A/B 两半**：B 需要 DPAPI 密码库和提权（`MpCmdRun`），A 不需要。
两者都能挂计划任务（同一用户的 `Interactive` 登录类型，DPAPI 可解），B 另加 `-RunLevel Highest`。

## 枢纽模型

下载、解压、校验、删源包**全部在一个固定的枢纽卷上完成**，最后一步才把成品移到目标路径：

```
D:\GameFlow\                     脚本、规则、skills（进 Git）
D:\GameHub\                      枢纽：_inbox\ _stg\ games\ _trash\ batches\ _reports\
    ↓ 投递（同卷 = rename，跨卷 = 复制+删源）
E:\wen\games\hgames\202609\<游戏名>\    每批指定，可在任意盘，也可留空之后再定
```

这么做换来四件事：**同卷恒成立**（认领归位与落地永远是 O(1) rename）、**Defender 排除项只有一条**、
**解压期 MAX_PATH 预算是固定值**、**目标目录只接收成品且永不进删除白名单**。
代价是跨卷投递要整体复制一次，时间与游戏体积成正比。

## 设计原则

**确定性优先。不猜。**

- **密码不猜** —— 你给的密码先试，失败才去密码库按命中次数排序试，**最多 8 次 7z 探测**，用尽就停下报告。字典爆破、从游戏名推导、从 README 里「读懂」一段话，全部硬性禁止。
- **类型不猜** —— 7-Zip 本来就按内容嗅探，不传具体 `-t` 类型名（传了反而会把能自动处理的情况变成硬失败）。
- **规则不猜** —— 重建分卷序列这类动作必须由批次条目显式声明。
- 不自适应、不加权评分。所有分支要么由显式规则决定，要么**停下来落一个具名状态等人**。唯一的例外是密码候选的**尝试顺序**可按命中次数排（只改先后，不改试哪些、试几次）。

**删除是本项目风险最高的操作**，由两条逐次执行的机器断言守住：

- **D1–D12** 十二条与条件（正确性判据，含逐条目 size 对账、卷集连续性、嵌套容器嗅探）
- **I6 路径围栏** —— 删除目标必须在枢纽根之内，规范化全路径前缀比对，不跟随 reparse point。**目标目录永不在删除白名单里**

不设人工确认闸门：一次覆盖整批的确认既验证不了 D1–D12，也发现不了路径算错，还会被疲劳性地点掉。

**引擎层吝啬，呈现层不吝啬。** 对账报告要真正好读。

## 从哪开始

**M0 = 在 Windows 上跑一次检测。** 一条命令，详见 [`docs/WINDOWS-CHECK.md`](docs/WINDOWS-CHECK.md)：

```powershell
git clone https://github.com/mmy420/gameflow.git D:\GameFlow
cd D:\GameFlow
powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\windows\Invoke-WindowsCheck.ps1 `
    -SampleGameDirs 'D:\你已解压的某个游戏'
```

这不是仪式感。本 SPEC 在 macOS 上撰写，凡是 Windows 特有的行为都只能靠官方文档推断，
标了 `【待测】` 的地方不实测就写不出正确的实现。其中几条会实质改变设计：

1. **环境快照** —— 装的是 7-Zip CLI 还是只有 WinRAR/Bandizip GUI、系统 ANSI 代码页、文件系统类型
2. **Codex 沙盒能否写到 `D:\GameHub`** —— 不能的话执行体 A 根本跑不起来
3. **`prefix_rule` 对 PowerShell 的拆分语义** —— 不通过的话每次解压都要人点一次，A 就失去无人值守的意义
4. **真实游戏包的最长内部条目路径** —— 直接决定目录名降级会不会频繁触发

之后按 A（只读）→ B（先关掉删除）→ B（打开删除）→ 投递 → C 的顺序推进，逐阶段任务与完成判据见 [`PLAN.md`](PLAN.md)。

## 出处

需求来自 Codex 会话「规划 Windows 游戏资源工作流」（`01a08eba-1b68-7b33-9a7e-242a5be1c22a`，2026-09-10），
该会话确立了批次驱动与两阶段拆分的方向。

在此基础上做了六条技术线的事实核查与一轮对抗式事实仲裁，推翻了原方案中的若干断言——影响最大的三条：
Codex 内置浏览器**没有**按任务指定下载目录的能力、「改后缀」在绝大多数情况下**根本不需要**、
游戏目录名的真实约束不是「非 ASCII」而是「必须能在系统 ANSI 代码页内无损表示」。

后续几轮又推翻了两条自己的断言：「B 必须有人在场」（那只在 `S4U` 登录类型下成立）、
「密码候选按命中排序会违反不自适应原则」（它不改变结果，只改变到达结果的路径）。
详见 §1.6 的对照表与 §12 决策台账。
